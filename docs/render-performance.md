# 性能优化与验收

> 从 0.24.0 起，本页中的画质对照、实验开关、性能报告与 GPU 计时仅在开发版提供。用户版固定高清，不采集这些数据；日常使用见[用户指南](user-guide.md)，智能体排查见[开发指南](developer-guide.md)。历史版本的数据保留原测试条件。

适用版本：0.23.1。日期：2026-11-03。[文档导航](README.md)

用户在 RTX 4060 Laptop、2K 屏幕、16GB 内存的另一台电脑上反馈过互动和播放卡顿、拖影，后续已确认 0.23.0 可以流畅使用，并提供了远端诊断数据。以下区分用户机器的采样、本机隔离验证和仍待确认的归因；不能把一种环境的结果替代另一种。

## 0.23.1：分清回调交付、主动跳帧与绘制工作

### 目标电脑 0.23.0 原始数据复核

两份 JSON 来自相同应用运行、同一渲染代数，高清档、GPU 数据复用关闭、兼容快照关闭，画布 2562 × 1368。`thinking-gpu.json` 的独立采集有 29 个有效 thinking 样本，GPU 均值 **1.460ms**、P95 **2.765ms**；`idea-gpu.json` 的另一轮混合采集为 idle 3 个、thinking 12 个、idea 14 个样本，分别均值 **1.852 / 1.930 / 2.677ms**。两轮均无 GPU 时钟失效和查询超时，轮询 CPU 最大约 0.2ms。

GPU 数据说明本轮模型绘制的 GPU 用时较短，但不能独立定位 DWM、浏览器合成或主线程调度。也不能用帧间隔 P95 减去 CPU 均值，或把 CPU 和 GPU 均值直接相加后称剩余部分为“纯等待”；两者可能重叠，且统计窗口不同。

原始窗口还有三点需要保留：

- 思考约 20fps 的窗口几乎没有主动跳帧；按相邻累计计数求差，较慢组约 20.80fps，208 个绘制帧仅跳过 1 次回调，CPU 窗口均值约 13.51ms。另一组约 31.14fps，872 个绘制帧对应 29 次主动跳过，CPU 窗口均值约 12.05ms。这支持继续观察应用限帧之外的回调交付，不能将全部差额归到 DWM。
- `averageRenderMs` 是应用加载以来的累计均值，不能当成本次思考的 CPU 均值。`idea-gpu.json` 中以 `intent:idea` 结束的四个窗口约 21–31fps；后面约 60fps 的窗口已经是 idle、`intent:null`。不能拿恢复待机后的数值证明动作期间一直是 60fps。
- `state/intent` 是每条报告的采样终点，窗口可能跨越动作切换。`gpuTiming` 是一整轮捕获的累计结果，结束后会随之后的报告重复携带；它不代表每个两秒窗口都重新取得这些 GPU 样本。两份报告的顶层聊天窗焦点信息，也不能还原每个历史窗口的聊天窗显示情况。

用户报告另行确认：DSH 桥重载后 `promptProtocol:2`、纯正文消息生效。这项验收仅覆盖已观察到的消息格式，不扩大为所有接入、取消和表演功能的重新验收。

### 新增的轻量帧节奏字段

`observeRaf(timestamp, enteredAt)` 在每次动画回调进入时、应用限帧判断之前记录。每次只更新有界环形数组和累计计数；不增加逐帧 IPC、GL 查询或独立轮询。近期数据最多保留 120 次回调／帧，并在读取时取至多约两秒的窗口、计算分位数。隐藏恢复或时间倒退会重置近期基线，不把隐藏时间误计为停顿。

| `sample` 字段 | 口径 |
|---|---|
| `rafCallbacks` | 本模型页面累计收到的动画回调数，包括随后被限帧跳过的回调 |
| `rafRecentSamples`、`rafWindowMs`、`rafRecentFps` | 近期原始回调窗口的样本数、跨度与频率；高刷新率时 120 条可能不足两秒 |
| `rafIntervalP95Ms`、`rafIntervalMaxMs` | 所有原始回调的时间戳间隔，区别于只统计实际绘制帧的 `frameInterval*` |
| `rafCallbackLagMeanMs/P95Ms/MaxMs` | JS 实际进入回调的时间减 rAF 时间戳；不同精度造成的小负数归零。它不是显示延迟或 DWM 排队用时 |
| `renderMeanMs`、`renderP95Ms` | 最近实际渲染帧的 CPU 均值和 P95，使用同一近期帧窗口 |
| `sampleRafFps`、`sampleFps` | 两次报告之间分别收到多少回调、完成多少绘制，除以同一个 `sampleWindowMs` |
| `sampleSkippedFrames` | 同一报告窗口中应用主动跳过的回调数量 |
| `sampleRenderMeanMs` | 同一报告窗口内 `totalRenderMs` 增量除以 `frames` 增量，独立于生命周期 `averageRenderMs` |

首条报告、页面重载、缺失或倒退的累计计数不能形成有效差值，对应 `sample*` 派生值为 `null`；没有实际绘制帧时 CPU 窗口均值也为 `null`。较慢的回调频率和极少主动跳帧说明下一步应检查回调之外的工作与交付节奏；仅凭这些字段仍不能分辨是浏览器渲染管线、桌面合成、其他主线程工作还是平台调度。验证与仍待确认的事项见[0.23.1 记录](release-validation-0.23.1.md)。

`rafRecent*` 最多使用 120 个原始回调：240Hz 时仅覆盖约 0.5 秒；`renderMeanMs` 的最近 120 个实际绘制帧在 60fps 时约为两秒，两套近期窗口不必同长。需要跨字段对比时优先选择主进程的 `sampleRafFps/sampleRenderMeanMs/sampleFps`，三者共享同一个报告窗口；rAF lag 仍不代表呈现延迟。

### 减少原生窗口重复更新

原生 `setShape` 影响桌面窗口的可见／输入区域。之前保护区域紧跟角色微小摆动时会反复变化，几何更新还会重复抬升工具窗口层级。0.23.1 用 `desktop/stable-pet-shape.cjs` 为保护区域保留少量有界余量，模型仍在已有保护内时复用原生区域；超出时立即扩张或重建。几何改变不再自动重复 `raiseTools` 或 `setAlwaysOnTop`，显示、隐藏、置顶及需要恢复控件层级的事件仍沿专用路径处理。

已有各边保护距离 `P = 18 × max(1, petScale)` DIP 是最低要求；稳定包络通常按各边 1.5P 构造，上限 2P，额外空白保护不会无界扩大。它仅决定原生窗口保护，头部、胸前、盆和拖动的精确判断继续使用实时模型位置。字幕和提示框独立管理，消失即移除；悬浮球／聊天窗口每次重新扣除，不能缓存旧排除区域。隐藏、重载、重置和摆放变化都会使旧包络失效。

这项优化减少的是原生窗口更新与层级操作。其调用次数、点击覆盖和真实画面要分别验收，不能把次数下降直接换算成目标电脑 FPS 提升，也不以此宣布 DWM 根因已确认。

本机同生产路径的八场景对照中，`setShape` 总调用由 446 降至 51（减少 88.57%），采样阶段重复 `moveTop` 从 674 降至 0。两版在本机 240Hz 屏幕上均接近 60fps，新版为 59.83–60.13fps、帧间隔 P95 16.7–17ms。八张独立捕获中，alpha≥32 的模型像素均落在实际原生 shape 与实时工具窗口排除规则允许的区域内；其中四个场景另经人工画面检查，未发现新增框裁切。这证明减少了原生调用并覆盖了这些局部验收，不代表目标电脑的帧率增幅或全部鼠标交互都已实测。

## 0.23.0：帧时钟修正与手动 GPU 计时

用户反馈 0.22.3 的独占 GL 状态路径明显改善了思考动作，但还不够平稳。新的代码排查发现：动画帧时间戳可能舍入到 0.1–1ms，60Hz 的一次正常回调可能显示为 `16.6ms`，小于理论 `16.666…ms`。旧限帧门槛会因此误跳帧。现在保持固定截止时间网格并接受不超过 1ms 的时间戳误差，同时限制相邻绘制的最小间隔，避免长停顿后追赶出几乎零间隔的帧。动作仍按真实经过时间推进，隐藏后仍重置时钟。修复位于 `src/shared/render-performance.mjs`，不改变模型参数、手臂绘制或 GPU 档位。

目标电脑的 0.22.3 报告已确认：高清、GPU 数据复用关闭时，独占状态路径把思考的 `drawSubmit` 均值从 38.77ms 降到 1.63ms，`stateSave` 从 37.47ms 归零；思考稳态约 30.09fps，帧间隔 P95 45.8ms，仍有优化空间。这里的 P95 是尾部帧间隔，不能减去各阶段的平均 CPU 耗时后，将差值称为“未统计的 GPU 等待”；两者统计口径不同，需按帧关联或另测 GPU。`1000 / P95` 也不是这段时间的平均帧率。此外，报告中的 `idea` 由带实际语音的 `avatar_speak` 触发，与静默固定思考并非同一负载，不能仅凭这两个样本断言瓶颈一定来自思考姿态的蒙版。

这能修正软件调度错误，但不能据此认定所有机器都稳定 60 帧，或把剩余停顿都归因于显卡。CPU `drawSubmit` 只表示提交这次绘制花了多久；GPU 执行和 Windows 最终呈现需要分开观察。

### 收集一次 GPU 用时

1. 保持当前更顺的档位和相同角色大小。打开“设置 → 性能与画质”，点击 **“采集 GPU 用时（15 秒）”**。
2. 在这 15 秒内复现固定思考与“想到了”；需要对比不同动作时分别采集，记录当前档位和缓存／状态快照选项。
3. 从开始计时约 20 秒后点击“复制性能诊断”。查询结果最多再等待 3 秒排空，加上现有约 2 秒状态同步；界面可显示“等待诊断结果…”，这不代表仍在采集。隐藏或重载模型会提前停止，无需在等待中重复点击。
4. 也可由已配对的智能体读取 `GET /api/performance` 的 `sample.gpuTiming`。这个 GET **只读取结果，不启动采样**；没有新增远程启动采样接口。

平时不探测计时扩展、不创建 GL query。手动采集才尝试 `EXT_disjoint_timer_query`，最多采集 15 秒，每至少 500ms 选取一帧，以异步查询取得 GPU 用时；不使用 `gl.finish()`、`gl.flush()` 或像素回读来等待完成。查询覆盖本帧的绘制状态设置、清屏与 SDK 完整绘制，包括蒙版与镜像手臂，不包含 DWM 合成、显示器扫描或端到端输入延迟。

| `sample.gpuTiming` 字段 | 含义 |
|---|---|
| `supported`、`active`、`reason` | 支持情况、是否仍采集以及状态／停止原因；未开始时不代表不支持 |
| `pending`、`samples` | 待返回查询数与有效样本数；没有有效样本不能当作 GPU 耗时为零 |
| `gpuMeanMs`、`gpuP95Ms`、`gpuMaxMs` | 有效样本的 GPU 执行用时，单位 ms；与 CPU 阶段计时不能相加 |
| `phases` | `idle/thinking/idea/speaking/other` 的分组样本及用时，避免把待机与思考平均在一起 |
| `disjointCount`、`timeoutCount` | GPU 时钟失效或结果超时次数；失效数据不作为正常耗时样本 |
| `pollCpuMaxMs` | 查询结果轮询本身的最大 CPU 耗时，用于识别诊断工具的影响 |

`reason` 可为 `not-started/capturing/draining/completed/stopped/unsupported/observer-overhead/timer-error/disposed`。不支持扩展时明确显示原因，不切换软件渲染来“补测”；一次轮询超过 8ms 会自动停测并标记 `observer-overhead`，此轮不能当作无扰动性能基准。隐藏、模型重载或停止采集后的状态也要结合有效样本数判断。

GPU 计时是可选诊断，日常流畅度仍要观察实际画面与帧间隔。相关验证口径见[0.23.0 验证记录](release-validation-0.23.0.md)；下文各历史数据保留原测试版本，不代表本版在目标电脑的实测结果。

## 0.22.1：思考仍卡顿时收集实际数据

后续录像确认均衡档仍有问题：思考阶段多次短暂停住再跳到下一姿态，同时聊天窗口仍在更新。源动作只有一次加载，不能把它描述为反复下载导致。原来的离屏基准没有覆盖用户的完整呈现环境，也不能据此认定问题已解决。

更新并重启后，复现一次思考卡顿，打开“设置 → 性能与画质 → 复制性能诊断”。也可让已配对的 DSH 请求 `GET /api/performance`；`GET /api/state` 与 MCP `avatar_state` 的 `rendering` 是不带历史的摘要。

报告每两秒接收一次本地计数，最多保留二十条近期样本，没有逐帧 IPC，也不上传到外网；复制内容不含聊天、配对码、API 密钥或模型路径。主要字段：

| 字段 | 用途 |
|---|---|
| `version`、`quality` | 确认实际运行版本和档位 |
| `sample.gpuRenderer`、`gpuVendor` | 实际 WebGL/ANGLE 设备，不能用“电脑安装了4060”代替 |
| `hardwareAcceleration`、`gpuFeatures`、`flags` | 是否启用硬件渲染、软件回退或相关进程参数 |
| `sample.sampleFps`、`sampleWindowMs` | 相邻两次采样间实际完成的模型绘制次数与时间 |
| `visible`、`petFocused`、`chatFocused`、`sample.documentVisibility`、`rendererPriority` | 原生窗口、网页可见性与渲染进程优先级是否一致；优先级读不到时为 null |
| `frameIntervalP95Ms`、`frameIntervalMaxMs` | 最近约两秒、至多120条记录的帧间隔，包含真正的长停顿 |
| `renderP95Ms` | 模型更新及提交绘制的 CPU 耗时，不是 DWM 最终呈现时间 |
| `stageAverageMs` | 同一采样窗口内行为、物理、模型更新、手部图层调整和绘制提交的单帧平均耗时；绘制提交不等于 GPU 完成时间 |
| `wallElapsedMs`、`logicElapsedSeconds` | 活跃状态下实际时间与动作逻辑时间；隐藏时间不计为停顿 |
| `native.shapeChanges`、`shapeMaxMs` | 原生保护区域变更的次数和最大调用耗时 |
| `samples` | 最近各阶段的记录，便于对比待机和思考 |

第一条样本的 `sampleFps` 为 null，尚无完整采样窗口；`ageMs` 较大表示数据已过时。若模型绘制本身仍约60帧而屏幕录像跳帧，应继续检查原生呈现，不能将绘制次数直接当作屏幕实得帧率。本版新增的是定位能力，没有宣称已解决目标电脑的思考卡顿。

## 使用设置

“设置 → 性能与画质”提供以下模式，选择后自动保存并重新加载模型；本次表演会停止。

| 模式 | 帧率上限 | 最大贴图边长 | 画布像素上限 | 适合 |
|---|---:|---:|---:|---|
| 自动 | 随选中档位 | 随选中档位 | 随选中档位 | 默认；物理内存不超过 20GiB 选均衡，其余选高清 |
| 均衡 | 60 | 3072 | 2560 × 1440 | 16GB、2K 及同时使用多个 AI 应用 |
| 省资源 | 30 | 2048 | 1920 × 1080 | 更低占用，接受较低帧率 |
| 高清 | 60 | 4096 | 3840 × 2160 | 大幅放大角色、较高内存余量 |

均衡和省资源关闭多重采样抗锯齿，高清保留；所有模式都关闭未使用的深度和模板缓冲。像素预算只影响清晰度，不改变角色大小、屏幕位置或点击坐标。物理内存仅在本机解析，不上报服务。

## 改动依据

- 原先每个显示器动画帧都执行 Cubism 模型、物理和蒙版绘制，高刷新率屏幕会做大量重复工作。现在按时间控制渲染频率，保持动作真实时长；不能用简单隔帧方法把 144Hz 屏幕误降到 48 或 30 帧。
- 五张原贴图包含 8192 像素长边。先读 PNG 头部，在位图解码入口请求目标大小，顺序上传并及时释放临时位图和画布。当前模型 RGBA 上传量由 4096 档约 208MiB，降到 3072 档约 124MiB；这不是完整进程或整机内存数字。
- 隐藏窗口后停止动画帧、模型和物理更新，重新显示时重置计时，避免补算隐藏期间的大步长。保留声音与聊天通道；继续保留 Windows 原生透明度修复，防止遮挡 DSH/Codex 绘制。
- 原生窗口在相同位置与输入状态下不再反复调用 setBounds、setIgnoreMouseEvents 和 moveTop；HiDPI 下也比较原生舍入后的结果。模型拖动合并位移、限制同时在途的 IPC，释放时保留最后一段位移。
- 命中保护区域向外量化，减少浮点微动引发的 React 与原生更新。精确摸头、敲盆、胸前判断仍使用真实模型几何。
- 每次透明清屏前显式恢复默认 framebuffer、完整颜色通道与非裁剪状态，防止 SDK 遗留状态限制清屏。此项是防御处理，尚不能据此断言远端电脑拖影的唯一原因。

没有减少作者物理组、删掉手臂镜像或降低蒙版数量；这些路径承担头发、身体物理和手臂正确分层。

## 0.22.0 本机真实模型对照（历史记录）

环境：Windows、Electron 39.8.10、RTX 4060 Laptop、40GB 物理内存。旧版固定为 `d3fb1dd`；新版显式选择均衡档。每次独立启动隔离 Electron，随机回环端口和独立 profile，不连接用户的 DSH、在线语音或大模型。offscreen 固定高刷新交付上限，按真实模型帧记录，覆盖待机、思考、讲述、摸头、敲盆、暂停和恢复。

| 2560 × 1440、DPR 1 | 旧版 | 新版均衡 |
|---|---:|---:|
| 稳态 Electron 进程工作集之和 | 1076.7 MiB | 751.4 MiB |
| 启动阶段采样峰值 | 1275.3 MiB | 1096.0 MiB |
| 可见动作的实际渲染速率 | 约 83–94 帧/秒 | 约 60 帧/秒 |
| 显式隐藏暂停 | 约 92 帧/秒 | 0 帧/秒 |

该轮稳态工作集减少约 30%，可见动作阶段没有超过 40ms 的帧间隔。摸头每帧计算耗时并未明显下降，收益主要来自少做重复帧、减少贴图和画布内存，以及给其他交互保留处理时间；不把限帧描述成每个动作都计算得更快。

另一轮 DPR 1.5 测试受 Windows 实际窗口大小约束，画布从 2561 × 1529 降到 2485 × 1483，稳态工作集从 1058.1MiB 降到 822.9MiB，约减少 22%。上述是本机隔离渲染数据，不是远端 16GB 机器实测，也不是整机物理内存的累计占用。

原生窗口 VM 计数使用生产主进程代码：100 次完全相同的几何通知，toggle.setBounds 从 100 次降为 1 次，setIgnoreMouseEvents 从 100 次降为 1 次，两个工具窗口的 moveTop 从 200 次降为 2 次。有效变化和显示/隐藏仍会重新设置。

本轮 291 项非交互 CI、TypeScript 检查和生产构建通过。实际 Electron 的窗口位置、指针恢复、悬浮球、菜单退出和设置持久化等 7 个入口通过；另 4 个 renderer 入口最终共 35 个测试结果通过，包含启动可见性竞态、隐藏暂停、恢复摸头以及既有语音编排。首轮 3 项原生鼠标观察器检查受旧测试目录低完整性执行环境影响；确认模块、源码和可执行文件 SHA256 与普通目录中的安装版完全相同后，针对该安装版重新执行，3 项全部通过。辅助程序未在本轮修改，也没有改变目录安全标签或全局安全策略。

## 0.22.0 基线复测与当前使用建议

```powershell
electron scripts/benchmark-renderer.cjs --variant=baseline --baseline-ref=d3fb1dd --model="<模型目录>"
electron scripts/benchmark-renderer.cjs --variant=after --baseline-ref=d3fb1dd --model="<模型目录>"
```

脚本需完整安装依赖和准备 SDK；请在正常用户目录的 Electron 环境运行。输出在忽略的 `output/performance-022/` 中，含源码摘要、真实画布尺寸、每阶段帧率和内存采样。不要把源码工作区安全标签造成的编译或子进程失败，当成渲染结果。

在目标测试机更新并重启后，优先保留该机器已观察到更顺的档位（本次用户反馈为高清），按相同角色大小分别测试固定思考、“想到了”、连续摸头、连击敲盆、讲述、拖动缩放和隐藏恢复。不要同时切换多个实验选项。若仍有拖影，记录动作、屏幕刷新率、帧间隔与短视频；需要继续定位时再手动采集 GPU 用时。均衡的像素预算更低，不代表每台机器上一定更快。
