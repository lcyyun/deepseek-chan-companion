# 性能优化与验收

适用版本：0.22.1。日期：2026-11-03。[文档导航](README.md)

用户在 RTX 4060、2K 屏幕、16GB 内存的另一台电脑上反馈：互动和播放轻微卡顿、拖影。本轮先处理可复现的重复工作与内存开销。没有在那台电脑上直接测量，因此仍需用户更新后复验。

## 0.22.1：思考仍卡顿时收集实际数据

后续录像确认均衡档仍有问题：思考阶段多次短暂停住再跳到下一姿态，同时聊天窗口仍在更新。源动作只有一次加载，不能把它描述为反复下载导致。原来的离屏基准没有覆盖用户的完整呈现环境，也不能据此认定问题已解决。

更新并重启后，复现一次思考卡顿，打开“设置 → 性能与画质 → 复制性能诊断”。也可让已配对的 DSH 请求 `GET /api/performance`；`GET /api/state` 与 MCP `avatar_state` 的 `rendering` 是不带历史的摘要。

报告每两秒接收一次本地计数，最多保留二十条近期样本，没有逐帧 IPC，也不上传到外网；复制内容不含聊天、配对码、API 密钥或模型路径。主要字段：

| 字段 | 用途 |
|---|---|
| `version`、`quality` | 确认实际运行版本和档位 |
| `sample.gpuRenderer`、`gpuVendor` | 实际 WebGL/ANGLE 设备，不能用“电脑安装了4060”代替 |
| `hardwareAcceleration`、`gpuFeatures`、`flags` | 是否启用硬件渲染、软件回退或相关进程参数 |
| `sample.sampleFps`、`sampleWindowMs` | 相邻两次采样间实际完成的模型绘制次数与时间 |
| `visible`、`petFocused`、`chatFocused`、`sample.documentVisibility`、`rendererPriority` | 原生窗口、网页可见性与渲染进程优先级是否一致；优先级读不到时为 null |
| `frameIntervalP95Ms`、`frameIntervalMaxMs` | 最近约两秒、至多120条记录的帧间隔，包含真正的长停顿 |
| `renderP95Ms` | 模型更新及提交绘制的 CPU 耗时，不是 DWM 最终呈现时间 |
| `stageAverageMs` | 同一采样窗口内行为、物理、模型更新、手部图层调整和绘制提交的单帧平均耗时；绘制提交不等于 GPU 完成时间 |
| `wallElapsedMs`、`logicElapsedSeconds` | 活跃状态下实际时间与动作逻辑时间；隐藏时间不计为停顿 |
| `native.shapeChanges`、`shapeMaxMs` | 原生保护区域变更的次数和最大调用耗时 |
| `samples` | 最近各阶段的记录，便于对比待机和思考 |

第一条样本的 `sampleFps` 为 null，尚无完整采样窗口；`ageMs` 较大表示数据已过时。若模型绘制本身仍约60帧而屏幕录像跳帧，应继续检查原生呈现，不能将绘制次数直接当作屏幕实得帧率。本版新增的是定位能力，没有宣称已解决目标电脑的思考卡顿。

## 使用设置

“设置 → 性能与画质”提供以下模式，选择后自动保存并重新加载模型；本次表演会停止。

| 模式 | 帧率上限 | 最大贴图边长 | 画布像素上限 | 适合 |
|---|---:|---:|---:|---|
| 自动 | 随选中档位 | 随选中档位 | 随选中档位 | 默认；物理内存不超过 20GiB 选均衡，其余选高清 |
| 均衡 | 60 | 3072 | 2560 × 1440 | 16GB、2K 及同时使用多个 AI 应用 |
| 省资源 | 30 | 2048 | 1920 × 1080 | 更低占用，接受较低帧率 |
| 高清 | 60 | 4096 | 3840 × 2160 | 大幅放大角色、较高内存余量 |

均衡和省资源关闭多重采样抗锯齿，高清保留；所有模式都关闭未使用的深度和模板缓冲。像素预算只影响清晰度，不改变角色大小、屏幕位置或点击坐标。物理内存仅在本机解析，不上报服务。

## 改动依据

- 原先每个显示器动画帧都执行 Cubism 模型、物理和蒙版绘制，高刷新率屏幕会做大量重复工作。现在按时间控制渲染频率，保持动作真实时长；不能用简单隔帧方法把 144Hz 屏幕误降到 48 或 30 帧。
- 五张原贴图包含 8192 像素长边。先读 PNG 头部，在位图解码入口请求目标大小，顺序上传并及时释放临时位图和画布。当前模型 RGBA 上传量由 4096 档约 208MiB，降到 3072 档约 124MiB；这不是完整进程或整机内存数字。
- 隐藏窗口后停止动画帧、模型和物理更新，重新显示时重置计时，避免补算隐藏期间的大步长。保留声音与聊天通道；继续保留 Windows 原生透明度修复，防止遮挡 DSH/Codex 绘制。
- 原生窗口在相同位置与输入状态下不再反复调用 setBounds、setIgnoreMouseEvents 和 moveTop；HiDPI 下也比较原生舍入后的结果。模型拖动合并位移、限制同时在途的 IPC，释放时保留最后一段位移。
- 命中保护区域向外量化，减少浮点微动引发的 React 与原生更新。精确摸头、敲盆、胸前判断仍使用真实模型几何。
- 每次透明清屏前显式恢复默认 framebuffer、完整颜色通道与非裁剪状态，防止 SDK 遗留状态限制清屏。此项是防御处理，尚不能据此断言远端电脑拖影的唯一原因。

没有减少作者物理组、删掉手臂镜像或降低蒙版数量；这些路径承担头发、身体物理和手臂正确分层。

## 本机真实模型对照

环境：Windows、Electron 39.8.10、RTX 4060 Laptop、40GB 物理内存。旧版固定为 `d3fb1dd`；新版显式选择均衡档。每次独立启动隔离 Electron，随机回环端口和独立 profile，不连接用户的 DSH、在线语音或大模型。offscreen 固定高刷新交付上限，按真实模型帧记录，覆盖待机、思考、讲述、摸头、敲盆、暂停和恢复。

| 2560 × 1440、DPR 1 | 旧版 | 新版均衡 |
|---|---:|---:|
| 稳态 Electron 进程工作集之和 | 1076.7 MiB | 751.4 MiB |
| 启动阶段采样峰值 | 1275.3 MiB | 1096.0 MiB |
| 可见动作的实际渲染速率 | 约 83–94 帧/秒 | 约 60 帧/秒 |
| 显式隐藏暂停 | 约 92 帧/秒 | 0 帧/秒 |

该轮稳态工作集减少约 30%，可见动作阶段没有超过 40ms 的帧间隔。摸头每帧计算耗时并未明显下降，收益主要来自少做重复帧、减少贴图和画布内存，以及给其他交互保留处理时间；不把限帧描述成每个动作都计算得更快。

另一轮 DPR 1.5 测试受 Windows 实际窗口大小约束，画布从 2561 × 1529 降到 2485 × 1483，稳态工作集从 1058.1MiB 降到 822.9MiB，约减少 22%。上述是本机隔离渲染数据，不是远端 16GB 机器实测，也不是整机物理内存的累计占用。

原生窗口 VM 计数使用生产主进程代码：100 次完全相同的几何通知，toggle.setBounds 从 100 次降为 1 次，setIgnoreMouseEvents 从 100 次降为 1 次，两个工具窗口的 moveTop 从 200 次降为 2 次。有效变化和显示/隐藏仍会重新设置。

本轮 291 项非交互 CI、TypeScript 检查和生产构建通过。实际 Electron 的窗口位置、指针恢复、悬浮球、菜单退出和设置持久化等 7 个入口通过；另 4 个 renderer 入口最终共 35 个测试结果通过，包含启动可见性竞态、隐藏暂停、恢复摸头以及既有语音编排。首轮 3 项原生鼠标观察器检查受旧测试目录低完整性执行环境影响；确认模块、源码和可执行文件 SHA256 与普通目录中的安装版完全相同后，针对该安装版重新执行，3 项全部通过。辅助程序未在本轮修改，也没有改变目录安全标签或全局安全策略。

## 复测

```powershell
electron scripts/benchmark-renderer.cjs --variant=baseline --baseline-ref=d3fb1dd --model="<模型目录>"
electron scripts/benchmark-renderer.cjs --variant=after --baseline-ref=d3fb1dd --model="<模型目录>"
```

脚本需完整安装依赖和准备 SDK；请在正常用户目录的 Electron 环境运行。输出在忽略的 `output/performance-022/` 中，含源码摘要、真实画布尺寸、每阶段帧率和内存采样。不要把源码工作区安全标签造成的编译或子进程失败，当成渲染结果。

在 16GB 测试机更新并重启后，先保留“自动”，确认显示“均衡”；按相同角色大小分别测试连续摸头、连击敲盆、讲述动作、拖动与缩放，以及隐藏后再显示。如果仍有拖影，请记录出现时的动作、屏幕刷新率和短视频，以便区分绘制残留、帧率不均或显示器本身的响应。
