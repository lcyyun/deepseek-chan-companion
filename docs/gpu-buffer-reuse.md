# 思考状态的 GPU 绘制对照

版本：0.22.2。日期：2026-11-03。[文档导航](README.md)

## 用户数据确认了什么

0.22.1 的测试机报告确认使用 NVIDIA RTX 4060 Laptop / ANGLE D3D11、硬件加速开启、均衡档生效、窗口和网页可见。待机稳态约60帧，思考约18–19帧；模型更新约8ms基本不变，而绘制提交从约6–7ms增至约41ms。

这支持优先检查 `drawModel()` 内的绘制提交。83.4ms 是 p95／最慢帧间隔，不是每帧固定83.4ms，不能用其倒数宣称实际只有12帧。硬件渲染正常也不能据此完全排除驱动、功耗或负载条件。

同模型的 WebGL 调用对照显示：思考没有让蒙版成倍增加，待机与思考均约92次蒙版网格绘制；普通网格仅增加约10个。持续阶段没有反复创建或编译 shader。每帧却有约1700次 `bufferData`，纹理坐标、索引等不变数据也被重复上传。SDK 的蒙版准备发生在绘制顺序遍历之前，单独调整手部层序不会改变蒙版分组。

## 实验优化做了什么

`src/renderer/mesh-buffer-cache.ts` 为每个渲染器、每个网格维护独立的顶点／纹理坐标／索引缓冲。稳定内容复用；顶点跨帧更新，同帧发生反射或还原仍按真实内容重新上传。原始手臂与镜像手臂不共用顶点缓存。

保留 SDK 原有绘制、蒙版与 shader 算法，以及 `bufferData` 的更新语义。未知参数、内容变更或不兼容结构走原路径；临时 GL 拦截在正常返回和异常退出时都恢复。销毁模型时释放缓冲。没有通过 `gl.finish()` 把等待挪到另一个计时区间，也没有关闭硬件加速或更改系统设置。

## 已验证与尚未证明的部分

- 确定性真实模型对照覆盖20个场景，包括思考入场／保持／退出、加载环、大半身、左右举指、双手抚胸、摸头松手、瞳孔缩放和敲盆。重复旧路径确认确定性后与新路径比较，截图像素相同、参数相同，WebGL无错误。
- 在与测试机相同的2562×1368画布、DPR1.5条件下，思考期间真实 `bufferData` 调用约1700→521次/帧，上传约1.262→0.356MiB/帧，分别减少约69%和72%。蒙版和正常绘制次数保持一致。
- 未包装 GL 方法的本机对照仍全部约60帧；缓存路径引入额外 CPU 内容校验和更多 GPU 缓冲对象。最终一轮思考平均单帧工作从约8.9ms增至10.4ms，双手抚胸约10.0ms增至12.1ms；进程工作集也有增加，单次内存峰值波动较大。因此**不能宣称本机整体加速或内存下降**，也尚未证实远端约41ms的阻塞已消失。

基于这些取舍，本功能默认关闭。它是针对提交瓶颈的可回退实验路径，不是对所有硬件强制启用的设置。

## 在出问题的电脑上怎样对照

1. 更新到0.22.2并完整退出、重新启动桌宠，保留原模型、位置、大小、均衡档和DSH会话。
2. 先保持“GPU 数据复用（实验）”关闭，重复同一段思考，稳定后复制性能诊断。
3. 在“设置 → 性能与画质”勾选该选项。等模型重新加载后，再触发相同思考；不要把重新加载本身的耗时当作动作卡顿。
4. 约10秒后再复制诊断，比较 `sampleFps`、`frameIntervalP95Ms`、`stageAverageMs.drawSubmit` 和实际画面。若没有收益或更差，取消勾选即可恢复原路径。

诊断中的 `quality.cacheMeshBuffers` 是用户选择，`sample.meshBufferCacheEnabled` 是实际是否启用。`meshBufferUploads / meshBufferUploadSkips / meshBufferUploadBytes / meshBufferCount` 仅统计新路径；关闭时为零不表示旧路径没有上传。

`stageAverageMs.stateSave / sdkDraw / stateRestore` 是 `drawSubmit` 内部的细分，不能再和 `drawSubmit` 相加；都属于渲染线程墙钟时间，不是独立 GPU 完成时间。

## 维护者复现

`scripts/benchmark-thinking-gl.cjs` 支持开关缓存、固定CSS画布／DPR，以及 `--gl-profile=off`。性能结论必须来自关闭 GL 方法包装的对照；带包装的运行只用于调用量分析。`scripts/verify-render-equivalence.cjs` 使用固定时间步和随机源做真实模型像素对照；两者均使用隔离 profile 和本地模型，不连接用户正在运行的桌宠或 DSH。
